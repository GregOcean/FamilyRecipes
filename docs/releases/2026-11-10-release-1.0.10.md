## 5. 审计旧菜系（Mac 终端）

退出服务器 SSH，回到 Mac 仓库。下面提示输入的是 App 数据管理员邮箱和 App 密码，不是 SSH/MySQL 密码。账号 ID 必须与服务器 CATALOG_ADMIN_USER_ID 相同。

```bash
cd /Users/wangyang/Documents/personal_projects/FamilyRecipes
printf 'App 数据管理员邮箱: '
read -r fr_admin_email
python3 backend/scripts/seed/refine_cuisines.py --login-email "$fr_admin_email"
```

默认仅审计，没有 LLM 调用：eligible_not_queued 为尚未入队的候选数，labels 是其旧分类分布，sample 为前 20 个 ID 和标签，jobs 是任务状态统计。

规则：只处理 recipe_provenance 中的导入菜谱，且已有菜系全部是粗标签（东北菜/西北菜/南亚/非洲菜/其他）或未映射值。明确标签及别名（如 IN/印度菜）无需模型处理；已有具体分类的混合标签不处理；用户自行创建的菜谱不批量修改。缺失/待确认继续由原有补全队列处理，与本队列分开。

## 6. 先试跑 5 条

```bash
python3 backend/scripts/seed/refine_cuisines.py --login-email "$fr_admin_email" --apply --limit 5
```

该命令只入队，真正调用文字模型在服务器后台发生；沿用现有模型配置，会产生费用。每次处理一条，间隔至少十秒（与其他后台工作共享调度，实际速度可能更慢）。关闭 Mac 或 SSH 不会中断队列。

服务器查看结果：

```bash
mysql family_recipes -e "SELECT status,COUNT(*) AS count FROM recipe_cuisine_refinement WHERE taxonomy_version='cuisine-v2-india' GROUP BY status;"
mysql family_recipes -e "SELECT j.recipe_id,r.name,j.status,j.original_cuisines,j.result_json,j.attempts,j.last_error FROM recipe_cuisine_refinement j JOIN recipe r ON r.id=j.recipe_id WHERE j.taxonomy_version='cuisine-v2-india' ORDER BY j.created_at DESC LIMIT 10;"
```

complete=已追加具体菜系；needs_review=缺乏依据/结果不兼容，保持原标签；stale=排队后内容或标签发生变化，未应用；failed=请求/解析失败，最多三次，间隔十分钟。pending/running=等待/处理中。原标签不删除，original_cuisines 和 result_json 保存历史标签和模型依据。

## 7. 全量排队（Mac）

试跑结果可接受后：

```bash
python3 backend/scripts/seed/refine_cuisines.py --login-email "$fr_admin_email" --apply --all
```

脚本每批至多 100 条，把剩余候选逐批排队。重复运行或网络中断后重跑不会重复入队同一版本任务；不会自动重新调用 needs_review/stale/已耗尽失败次数的任务。可随时运行不带 --apply 的审计命令查看进度。

不保证所有粗分类都能细分：比如通用做法不能可靠区分东北三省，应保留原标签，而不是强行分省。此次不会清除历史标签或以模型结果覆盖用户编辑。

## 8. 暂停与排查

把 RECIPE_CLASSIFICATION_ENABLED 改为 false 并重启，可暂停两个分类队列，已有结果保留。先查看失败数量和 last_error，再决定是否重新尝试；不要批量删队列表来无限重试。管理员接口 GET/POST /api/catalog/cuisine-refinement 提供审计/入队，普通账号和匿名访问均被拒绝。
