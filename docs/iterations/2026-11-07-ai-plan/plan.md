# AI 辅助录入与整理计划

日期：2026-11-07。状态：待实施；先验收现有功能。本文件仅保存讨论结论，不代表已接入模型或实现功能。

## 目标与约束

减少库存、菜谱、点菜和备菜的录入成本。继续使用单机 Spring Boot、MySQL 和本地媒体存储；暂不引入消息队列。AI 不决定权限，不直接执行库存变更，不覆盖用户已经修改的内容。

## 第一阶段：共用识别草稿能力

### 小票入库

支持拍摄整张小票、相册选图，异步识别商品行。扫码订单号不等于取得明细；商家二维码需要对应接口，不承诺通用解析。

流程：上传图片 → 提取商品行 → 匹配公共食材库 → 待入库清单 → 批量确认 → 入库。保留原始商品名、规格、数量、单位、可选购买时间、标准食材候选及原文依据；跳过非食品。区分数量、重量、单价、总价和折扣。无法判定的字段留空、展示候选，不凭空补齐。支持重新拍照、逐行编辑、忽略、撤销和重复小票提示。

同一提交重试不得重复入库；重复检测使用图片指纹和商家、日期、金额、商品明细等信息提示，不能把相似的真实两次购物强制合并。

### 食材与包装照片

识别候选食材、规格及包装上明确印刷的日期和存储说明。看不清、遮挡、品种相近时要求确认。照片不能可靠判断新鲜程度或实际剩余保质期。

期限优先级：用户明确填写／包装标注 → 经维护的食材＋存储方式＋开封状态规则 → 提示用户填写。区分包装到期日与建议食用期限，记录依据。日期计算由后端完成，不让模型随意生成确定期限。改变存储条件不自动延长已经确认的期限。

### 标准食材匹配

共用于小票、照片、文字、菜谱整理：同义词、商品缩写、品牌规格映射到现有食材，保留商品原始信息。保留生鲜、熟食、腌制、干货等差异；不擅自合并牛肉与牛肉干等。精确词典优先，检索候选，再让模型辅助选择；无法匹配可暂存用户自定义条目，不直接污染公共库。

### 菜谱整理

外链、粘贴正文、截图均生成可编辑草稿。网页获取与模型解析分离：模型不能保证突破反爬、登录限制，也不能恢复已删除视频。获取失败仍保留链接，允许用户补截图和文字。

提取标题、用料、步骤、耗时、份数、口味等，保存来源。区分原文事实与 AI 建议；缺失用量留空或标注原文“适量”。不自动下载视频、不自动发布、不修改原作者菜谱。

## 第二阶段

- 语音转写后共用结构化解析，将一句话拆成库存、点菜或备菜草稿；操作前显示确认卡片，不直接发送群消息。
- 自然语言搜索：解析口味、时间、排除项、库存限制；搜索仅返回用户有权限访问的菜谱。
- 备菜辅助：候选菜单搭配、替代食材、制作顺序；数量汇总与单位换算由程序执行，缺少数量时提示。
- 菜谱标签：异步补充口味、主要食材和做法，保留来源和人工修正；公共冷启动数据先抽样审核。
- 按需翻译：保留原文，缓存译文，不覆盖用户原始菜谱。
- 推荐：程序召回与过滤，模型可对少量候选排序并解释。分别支持库存＋我会做、搜索意图、全库个性化探索；不每次发送全库，不把生成的新菜当作已有菜谱。

## 单机实现设计

新增持久任务表，记录账号、厨房、任务类型、输入引用、状态、重试次数、输入版本、输出草稿、模型／提示版本、错误及耗用量。状态为 queued/running/succeeded/failed/cancelled。数据库领取任务并设置租约，进程重启可恢复；外部请求超时、有限重试、限制并发，取消与过期结果不得再应用。

接口返回任务 ID；客户端显示进度，离开页面后仍可继续，重新进入读取结果。任务及媒体均做账号和厨房权限校验；应用结果时重新检查权限。

模型输出使用固定结构，后端校验字段、日期、数量、单位、候选 ID 与引用权限。格式合规不代表事实正确。对网页和 OCR 内容按数据处理，不能执行其中的指令。API 密钥仅留后端，只传任务必要内容；小票可能包含付款和会员信息，发送前尽量剔除不必要字段。

结果只能补充空字段或作为待接受建议；基于输入版本检查冲突，不能覆盖用户编辑或当前页面最新状态。入库确认带幂等键，由业务事务一次提交。可保留输入图片供核对，保存期限需实施前确定，沿用本地媒体回收机制。

## 实施顺序与验收

1. 公共食材匹配＋异步任务＋可编辑草稿基础。
2. 小票／包装照片入库，包含重复提交、模糊图、非食品、数量金额混淆和权限测试。
3. 菜谱正文／截图整理，测试缺失用量、不完整截图、外链失败和来源保留。
4. 语音复用草稿；再扩展搜索、备菜、推荐和翻译。

先收集经允许的代表性测试样本，比较识别准确率、修正次数、响应时间和每次成本，再选供应商及模型；当前不锁定厂商、价格或准确率承诺。验收必须包含断网重试、服务重启、用户中途编辑、取消、退出账号及重复入库。
