# 发现页超时与分层菜系

## 发现页

旧推荐分数对每道候选菜谱嵌套查询 recipe_tag，并对大量同标签菜谱判断收藏/会做关联。在用户偏好稀疏、全库标签增加的场景中，大量无匹配结果需要重复扫描。之前关键词搜索性能测试没有覆盖这条路径。

改为先用非关联 DISTINCT 派生表汇总当前用户收藏/会做以及最近浏览的标签，再关联候选菜谱的标签。保留原有权重、踩的降权、随机种子、过滤先于分页和可见性检查。匿名发现直接计算种子随机分，不查询个人偏好。

临时 MySQL 8.4 测试：4000 菜谱、12000 标签、40 条收藏/会做/浏览偏好。偏好覆盖候选标签时旧排序约 91ms；偏好稀疏时旧排序超过 3000ms，被 MAX_EXECUTION_TIME 测试保护中断。新 browse 含计数和卡片加载约 24ms。数字为本机隔离数据集，不代表生产网络或服务器延迟。临时旧排序对照代码未保留，正式回归保留稀疏偏好的规模测试。

## 菜系

统一配置：backend/src/main/resources/cuisines.json。

- 中国：八大菜系；其他省级风味；家常与港澳台；历史东北/西北等粗粒度标签。
- 东亚：日本、韩国/朝鲜、蒙古。
- 东南亚：按国家。
- 欧洲：主要国家（包括俄罗斯），北欧及欧洲其他地区。
- 其他：印度单列、南亚（其他或未细分）、中东、南美、北美、中美洲与加勒比、非洲（北非/非洲南部/其他）、澳洲、大洋洲其他。

中国八大菜系对应的省份不在其他省级风味中重复。历史东北菜、西北菜无法可靠还原到具体省份，保留单独入口，不强行归省。

新增公开只读 GET /api/recipes/cuisines/tree，直接返回中/英文名称，无需 LLM 翻译。Android 菜系菜单逐级展开，每组支持选「全部」，当前值在筛选类别下方显示。API cuisine 支持地区键或原有具体标签。

兼容别名示例：JP/日本/日式，US/美式归北美，墨西哥菜归北美，IN/印度/India 归印度菜，土耳其菜归中东。既有标签不改写，通过匹配别名纳入筛选，详情页显示对应分类名称。后台分类与本地 classify_catalog.py 使用相同叶子分类表，避免继续扩张国家平铺列表。

## 验证与上线

后端回归 73 项，Android 编译与单元测试通过。包括稀疏偏好发现性能、相同种子排序稳定、分页不重复、区域筛选包含旧标签且不泄露私有菜谱、匿名访问英文分类树。

需要更新后端和 Android；分层菜单本身无需改写旧标签；随后增加了定向回填队列表迁移，不清库、不重新导入、不重跑全部翻译。此轮修改尚未发布，线上 1.0.9 不会自动获得修复。

## 回填边界

分类树和明确旧标签（例如 IN、印度菜）的兼容不需要改写数据库。原有「待确认」或缺失标签继续由 1.0.9 的补全任务处理；failed 达到上限、needs_review 不会自动无限重试。

历史「南亚」「东北菜」「西北菜」「其他」或不在分类映射中的标签，无法只靠别名准确分到国家/省份。若希望全库都能按新细分类筛出，需要先审计线上标签分布，再对这些记录定向重新分类。语义回填已实现独立管理员审计/入队入口和 refine_cuisines.py，尚未在线上执行。仅为导入的粗分类菜谱追加具体标签，不删除原标签；明确标签和普通用户新建菜谱不批量改写。原任务仍只补缺失分类。无需清库、重新导入或全量重翻译。
